# Architecture Decision Records

## 철학
측정 없이 판단하지 않는다. 한 번에 한 변수만 바꾼다. 결정론적으로 잴 수 있는 것은 LLM 없이 잰다. 모든 수치는 재현 가능해야 한다.

### ADR-001: 코퍼스는 실제 공개 문서와 합성 문서를 섞는다
**결정**: 실제 문서는 ALIO 공공기관 내부규정(사규) 원본 파일과, 같은 규정의 법제처 Open API 구조화 조문(파싱 정답 텍스트), 합성 문서는 가상 회사의 회의록·보고서·장애 보고서·런북·티켓·결재. AI Hub 데이터는 쓰지 않는다.
**이유**: 실제 문서만으로는 식별자·권한·문서 간 연결이 없어 질의 경로 셋 중 둘을 시험할 수 없다. 합성 문서만으로는 파싱 난이도가 사라지고 점수가 부풀어 오른다(합성 질의는 실제 질의보다 쉽다: Rahmani et al., SIGIR 2024, arXiv 2405.07767). AI Hub는 재배포 제약으로 저장소만으로 재현할 수 없다.
**트레이드오프**: 합성 문서의 현실감은 생성 품질에 달려 있다. 실제/합성 점수를 분리 보고해 차이를 드러낸다.

### ADR-002: 가상 IT 서비스 회사, 실제 규정은 NIA 내부규정 원문을 무가공 로컬 사용
**결정**: 가상 회사(약 200명, 8개 팀) 설정은 유지한다. 실제 규정은 NIA ALIO 공시 내부규정 95개를 원문 그대로 로컬에서만 쓴다. 기관명 치환 등 가공은 하지 않는다. 합성 문서는 기관명 없이 규정명·조항만 참조한다(예: "여비규정 제8조"). 원문과 정제 산출물은 커밋하지 않고 manifest(출처 URL·해시·수집일)로 재현한다.
**이유**: 후보 세 기관 모두 ALIO에 공공누리 표시가 없어 기관명 치환(2차적 저작물 작성)의 근거가 없다. 무가공 원문을 재배포하지 않고 로컬 평가에만 쓴다. 실존 기관 이름으로 회의록·티켓 같은 기록을 만들면 허위 기록이 되므로 합성 문서에는 기관명을 쓰지 않는다. NIA는 규정 95개가 법제처에 구조화 조문으로 모두 있어 파싱 정답을 자동으로 얻을 수 있고, 정보화·AI 관련 규정이 IT 회사 설정과 맞으며, HWP·HWPX 개정 버전 파일이 있어 실제 개정 이력을 쓸 수 있다.
**트레이드오프**: 규정 본문에 실제 기관명이 남아 가상 회사 설정과 이음새가 보인다. 저장소만으로는 재현되지 않고 사용자가 수집 스크립트를 실행해야 한다. 법제처 응답의 담당자 개인정보(담당자명·전화번호)는 정제 산출물과 manifest에서 제거한다.

### ADR-003: 합성 데이터는 시드 데이터를 먼저 정의하고 문서로 렌더링한다
**결정**: 인물·서비스·사건 타임라인·티켓 DB를 YAML/JSON으로 정의하고, Anthropic API 스크립트로 문서를 생성한다. 문서마다 생성 모델·프롬프트 해시·랜덤 시드·출처 사실 ID를 기록한다.
**이유**: 사실을 먼저 고정해야 문서 간 일관성과 정답 문서 목록을 생성 시점에 확보한다. 가상 기업 데이터를 조직 메타데이터(organizational metadata)에서 파생시키는 EnterpriseBench(arXiv 2510.27287)와 같은 방식이다. 실무 합성 평가셋 도구(Databricks `generate_evals_df`, Ragas `TestsetGenerator`)도 코드 파이프라인으로 생성한다. 재생성·감사가 가능해야 수치를 믿을 수 있다.
**트레이드오프**: 시드 데이터 설계에 초기 비용이 든다. 대화형 생성보다 느리게 시작한다.

### ADR-004: 모델 역할 분리 — 생성 Anthropic, 답변 OpenAI, 채점 Gemini
**결정**: 합성 생성은 Anthropic API, 시스템 답변은 OpenAI API, 답변 채점은 Gemini API(무료 등급 Flash). 구독(Claude Pro, ChatGPT Pro)은 개발 도구로만 쓴다.
**이유**: LLM 채점자는 자기 계열 출력을 선호한다(Panickssery et al., NeurIPS 2024, arXiv 2404.13076). 생성 계열 편향은 약하다는 결과가 있다(Rahmani et al.). 런타임 호출은 모델 버전·temperature 고정과 function calling이 필요해 API여야 한다.
**트레이드오프**: API 키 3개(+업스테이지)와 소액 비용. Gemini 무료 등급은 입력이 서비스 개선에 쓰이지만 공개 사규·합성 데이터만 보낸다.

### ADR-005: 검색 엔진은 OpenSearch, 정형 데이터는 SQLite
**결정**: OpenSearch(Apache-2.0, 무료)를 로컬 Docker 단일 노드(nori 플러그인)로 띄워 BM25·k-NN·hybrid(RRF, 정규화)·권한 filter. 티켓·결재만 SQLite. 계획 초안의 SQLite FTS5 + LanceDB는 쓰지 않는다.
**이유**: 사내 검색 실무의 대표 선택이고, 한국어 형태소 분석기(nori)와 hybrid 결합 방식 두 가지(RRF는 2.19부터)를 내장해 비교 실험을 엔진 안에서 할 수 있다. 임베디드 구성(실리콘투 사례)은 비용·egress 제약에서 나온 선택이었고 이후 pgvector로 옮겼다.
**버전·구성**: 3.x를 쓴다. hybrid 쿼리의 공통 filter가 k-NN 하위 쿼리에 효율적 사전 필터로 적용되는 것이 3.0부터다(그 전에는 하위 쿼리마다 filter를 복제). k-NN과 neural-search(hybrid, normalization·score-ranker processor)는 기본 배포판에 번들되어 있고, nori는 추가 플러그인 `analysis-nori`를 이미지 빌드 시 설치한다. k-NN 엔진은 효율적 필터링을 지원하는 faiss 또는 lucene(HNSW). 로컬 개발에서는 보안 플러그인을 끈다(`DISABLE_SECURITY_PLUGIN=true`). 권한은 앱 계층(ADR-010)에서 강제한다.
**트레이드오프**: Docker와 수 GB 메모리가 필요해 재현 비용이 올라간다(Docker Desktop 메모리 4GB 이상 권장). 유료인 관리형 서비스(Amazon OpenSearch Service)는 쓰지 않는다. hybrid 쿼리는 최상위 쿼리여야 하고 하위 쿼리는 최대 5개다.

### ADR-006: 임베딩은 BGE-M3 로컬
**결정**: BGE-M3를 로컬에서 돌려 Python에서 계산한 벡터를 `knn_vector`로 적재한다. OpenSearch ML 기능은 쓰지 않는다.
**이유**: 한국어를 지원하는 다국어 모델이고 무료이며 버전 고정으로 재현성이 좋다. 적재 경로가 단순하다.
**트레이드오프**: 로컬 연산 시간이 든다. API 임베딩과의 비교는 범위 밖이다.

### ADR-007: 구조 기준 청킹, 조문 분할은 파서와 독립
**결정**: 규정은 조 단위(경로 prefix 포함), 별표 표는 표 단위, 회의록은 안건, 장애 보고서는 섹션. 고정 길이(512토큰)를 비교 기준으로 둔다. 조문 분할은 파싱 결과 텍스트에 `제N조` 정규식을 적용한다.
**이유**: 파서마다 제목 인식이 달라, 분할을 파서에 맡기면 파서 차이와 청킹 차이가 섞인다.
**트레이드오프**: 규정 외 문서는 문서 유형별 분할 규칙이 필요하다.

### ADR-008: 파서 비교는 실제 사규에서만, HWP는 PDF로 변환
**결정**: HWP·HWPX → LibreOffice + H2Orestart → PDF를 기본 경로로 pypdf(기준선)·Docling·업스테이지를 비교한다. 변환 형식은 확장자가 아니라 파일 시그니처(HWP 5.x는 OLE 복합 문서, HWPX는 zip)로 판정한다. 변환 시 `FONTCONFIG_FILE=infra/fontconfig/fonts.conf`를 넘겨 HWP가 지정한 글꼴을 함초롬(HCR Batang/HCR Dotum)으로 대체하고, 규칙에 없는 글꼴은 HCR Dotum으로 고정한다. 업스테이지 HWP 직접 파싱은 공식 지원 확인 시 추가한다. 합성 문서는 Docling 하나로 처리한다.
**이유**: Docling은 HWP/HWPX를 지원하지 않는다(공식 지원 형식 문서). H2Orestart는 HWP 5.x와 HWPX를 모두 지원한다. 합성 문서는 깨끗해서 파서 차이가 나지 않는다.
**트레이드오프**: 변환 단계가 품질에 영향을 줄 수 있어, HWP 직접 파싱 결과가 있으면 함께 보고한다. headless soffice는 `FONTCONFIG_FILE` 없이는 한글이 빈칸인 PDF를 만든다(M1 실측, 함초롬을 설치해도 같았다). 쪽수·줄바꿈은 대체 글꼴에 좌우되지만, 파서 3종은 같은 PDF를 입력으로 하므로 상대 비교는 유효하다. 함초롬 글꼴은 사용자가 설치하며 저장소에 포함하지 않는다(상업적 재배포 금지).

### ADR-009: LangGraph로 조율하되 검색 추상화는 쓰지 않는다
**결정**: A·B 모두 LangGraph. LangGraph 그래프·`@tool`·`ToolRuntime`·모델 래퍼는 쓰고, LangChain의 retriever·vectorstore·loader·splitter는 쓰지 않는다. `retrieval` 패키지의 langchain/langgraph import 금지를 테스트로 강제한다.
**이유**: 이 프로젝트가 측정하는 대상(분석기 설정, hybrid pipeline, 권한 filter, 청킹)이 추상화 아래에 있고, 숨은 기본값은 실험을 오염시킨다. "프레임워크는 시작을 돕지만 프로덕션으로 갈수록 추상화 층을 줄이라"(Anthropic, Building Effective Agents).
**트레이드오프**: 검색 코드를 직접 작성·유지한다. 필요하면 `BaseRetriever` 어댑터를 얇게 추가한다.

### ADR-010: 권한은 서버가 주입하고 검색 전에 한 곳에서 강제한다
**결정**: 사용자 컨텍스트는 도구 인자가 아니라 LangGraph `ToolRuntime` context·MCP bearer 토큰으로 서버가 주입한다. 모든 경로는 `retrieval.authorized_*`에서 pre-filter를 적용한다. `run_sql`은 SELECT·허용 테이블·LIMIT·읽기 전용 연결.
**이유**: OWASP LLM06:2025 Excessive Agency — 사용자 컨텍스트에서 최소 권한으로 실행하고, 인가는 LLM이 아니라 downstream에서 완전 중재(complete mediation)한다. 호출자가 에이전트면 결과를 사람이 거르는 사후 안전판이 없다(실리콘투).
**트레이드오프**: 권한 모델이 문서 메타데이터에 의존해, 메타데이터 오류가 곧 권한 오류가 된다. 누설률 테스트로 방어한다.

### ADR-011: A는 MCP 서버, B는 MCP 클라이언트
**결정**: A는 도구 4개를 streamable HTTP MCP 서버로 노출한다. A의 LangGraph 에이전트는 자기 도구를 MCP로 호출하지 않고 in-process로 부른다. B의 에이전트가 A의 MCP 서버를 쓴다.
**이유**: 같은 코드베이스 안의 호출에 MCP를 끼우면 홉만 늘어난다. 인가를 `retrieval` 한 곳에서 강제하면 입구가 둘이어도 규칙은 하나다. 두 프로젝트로 MCP의 서버·클라이언트 양쪽을 다룬다.
**트레이드오프**: 입구가 둘이라 누설률을 두 경로 모두에서 측정해야 한다.

### ADR-012: 평가는 결정론 우선, 채점 모델은 사람 채점으로 검증
**결정**: 검색 지표·인용 정밀도·거절 정확도·누설률(카나리아)은 결정론으로 잰다. 정답성·근거 충실성만 Gemini가 0~3점으로 채점하고, 사람 채점 50건과 가중 Cohen's κ ≥ 0.6을 확인한다. 모든 비교에 부트스트랩 95% CI를 붙인다.
**이유**: LLM 채점과 사람 채점의 일치는 80% 수준이며 0~3 같은 좁은 척도가 권장된다(Databricks). 50문항 규모에서는 작은 차이가 우연일 수 있다.
**트레이드오프**: 사람 채점 시간이 든다. CI가 넓으면 주장할 수 있는 결론이 줄어든다.

### ADR-013: 질의셋은 검색 구현 전에 확정하고 dev/test를 나눈다
**결정**: 50문항(실제 20 / 합성 30)을 M4에서 확정하고 dev 20 / test 30으로 나눈다. 보고는 test만.
**이유**: 검색을 만든 뒤 질의를 만들면 잘 되는 질의로 치우친다. 튜닝한 문항으로 보고하면 과적합된 수치가 나온다.
**트레이드오프**: 유형별 문항 수가 적어 유형별 수치는 참고용이다.

### ADR-014: 실제 API 호출은 사용자가 직접 실행한다
**결정**: 하네스 step(Codex)은 스크립트와 mock 테스트까지만 만든다. `make generate`·`make eval`은 사용자가 실행한다. 에이전트는 `.env`를 열지 않는다.
**이유**: 하네스 에이전트는 작업 폴더와 네트워크에 접근할 수 있어, 키가 실행 로그에 남거나 의도치 않은 과금이 생길 수 있다.
**트레이드오프**: 생성·평가 단계마다 사용자 개입이 필요하다.

### ADR-015: 질의셋은 골드 50 + 실버 150, 비교는 짝 비교 부트스트랩
**결정**: 사람이 전부 검수한 골드 50문항으로 주장하고, 시드 데이터에서 자동 생성해 20%만 표본 검수한 실버 150문항으로 방향을 확인한다. 두 시스템 비교는 같은 문항 쌍의 짝 비교 부트스트랩 95% CI로 한다.
**이유**: test 30문항만으로는 작은 차이에서 신뢰구간이 겹쳐 결론을 내기 어렵다. 검색 평가는 채점 모델이 필요 없고 합성 문항의 정답은 시드 데이터에서 결정론적으로 나오므로 실버셋 비용이 거의 없다. 짝 비교는 문항 난이도 편차를 상쇄해 구간을 좁힌다.
**트레이드오프**: 실버셋은 합성 문항이라 실제보다 쉽다(ADR-001). 실버셋 수치로는 주장하지 않는다.

### ADR-016: 정답은 구간 단위로 표시하고, 주 지표는 문서 단위
**결정**: qrels를 `doc_id` + 조항 ID(사규) 또는 시드 데이터 사실 ID·문자 범위(합성)로 표시한다. 주 지표는 청크를 문서로 묶은 문서 단위 Recall@10·NDCG@10, 보조 지표는 구간 겹침 적중률.
**이유**: 청크 ID로 표시하면 청킹 방식마다 청크가 달라 구조 청킹 대 고정 청킹 비교가 무효가 된다. 문서 단위만 표시하면 "문서는 맞는데 조항이 틀린" 경우를 잡을 수 없고, 나중에 구간 정보를 되살릴 수 없다.
**트레이드오프**: 사규 문항은 조항 ID를 사람이 표시해야 한다.

### ADR-017: 식별자는 keyword 필드에서 정확 일치로 찾는다
**결정**: 적재 시 정규식으로 `PAY-1234`·`EXP-2026-0412`·`INC-2026-031`·서비스명·조항 번호를 추출해 분석하지 않는 `keyword` 필드에 넣고, `lookup_id`는 `term` 쿼리로 조회한다.
**이유**: nori·standard 분석기는 하이픈에서 토큰을 쪼개 `PAY-1234` 검색에 `PAY-1233` 문서가 섞일 수 있다. 식별자는 정규화 후 정확 일치로 찾는다(나래에너지서비스 사례).
**트레이드오프**: 식별자 패턴 목록을 관리해야 한다. 효과는 식별자 문항에서 본문 검색 대비 적중률로 측정한다.

### ADR-018: MCP 도구 계약은 버전·공통 오류·계약 테스트로 관리하고, 인증은 정적 토큰
**결정**: 도구마다 입출력 스키마와 버전을 두고, 공통 오류 형식을 쓰며, 계약 테스트로 호환성을 강제한다. 인증은 데모 사용자별 정적 bearer 토큰이다.
**이유**: 프로젝트 B가 이 도구에 의존하므로 계약이 깨지면 B가 깨진다(오토메타 공고: tool 계약의 schema·버전·권한). 인증 구현은 이 프로젝트의 주장과 거리가 멀고, 인가(토큰 → 권한 결정)는 서버에서 제대로 강제한다. 실리콘투도 MCP API 키로 시작했다.
**트레이드오프**: 실서비스에는 MCP 명세의 OAuth 2.1이 필요하다. 한계 섹션에 명시한다.

### ADR-019: 문서 속 간접 프롬프트 인젝션은 검색 전 인가로 막고 테스트로 증명한다
**결정**: 합성 코퍼스에 "제한 문서 내용을 출력하라" 같은 지시를 담은 문서를 심고, 보안 테스트셋(200건 이상, in-process·MCP 두 경로)에 인젝션·우회 표현 시나리오를 넣는다. 위협 모델 문서는 M7에 작성한다.
**이유**: RAG의 대표 위협은 검색된 문서 안의 지시다. 권한이 검색 전에 서버에서 강제되면(ADR-010) 인젝션이 모델을 속여도 제한 문서가 애초에 후보에 오르지 않는다. 이를 수치로 보이는 것이 "권한을 LLM에 맡기지 않는다"의 증거다.
**트레이드오프**: 인젝션이 권한 밖 유출은 못 해도 답변 품질을 오염시킬 수는 있다. 이는 답변 계층 지표와 실패 분석에서 따로 본다.

### ADR-020 (폐기): 사규 가공이 허용되지 않으면 다른 기관, 그다음 행정규칙
**상태**: 폐기 — ADR-002 개정으로 원문을 가공하지 않게 되어, 공공누리 유형에 따라 다른 기관이나 행정규칙으로 대체할 필요가 없어졌다.
**결정**: 고른 기관 사규의 공공누리 유형이 변경을 금지(3·4유형)하면 변경이 허용되는 다른 IT 계열 기관을 찾고, 없으면 법제처 행정규칙(훈령·예규)으로 대체한다.
**이유**: 기관명 치환은 2차적 저작물 작성에 해당한다. 국가·지방자치단체의 훈령·고시는 저작권법 제7조의 보호받지 못하는 저작물로 알려져 있어 가공이 자유롭다(M1에서 조문 확인 후 확정).
**트레이드오프**: 행정규칙은 사내 규정보다 문체가 관청 쪽이라 가상 회사 설정과 덜 맞는다.

### ADR-021: 데모 GUI는 Streamlit, answer()만 호출
**결정**: M8에 Streamlit 화면 두 개(사용자 전환 질의 화면, 결과표 뷰어)를 만든다. GUI는 `answer()`만 호출하는 얇은 껍데기다. 주 데모는 Claude Code를 MCP 클라이언트로 붙인 장면, 보조로 GUI를 쓴다.
**이유**: 같은 질문을 사용자만 바꿔 던져 허용·거절을 한 화면에 보여줄 수 있다. 핵심 결과가 나오기 전에 UI에 시간을 쓰지 않도록 마지막에 둔다.
**트레이드오프**: 운영용 웹 애플리케이션 수준의 UX는 범위 밖이다.

### ADR-022: 규정은 두 경로로 수집하고, 개정 날짜는 법제처 연혁을 기준으로 삼는다
**결정**: 법제처 Open API에서 현행·연혁 버전의 본문을 모두 받아 파싱 정답과 개정 날짜 기준으로 쓴다. ALIO 원본 파일(zip 취합본은 압축 해제)은 파싱 입력으로 쓴다. ALIO 파일마다 법제처 버전과 발령일자로 매칭해 근거와 신뢰도(정확/근사/실패)를 manifest에 남기고, 실패 파일은 파싱 평가 대상에서 제외한다. 파싱 대상은 현행본 전부와 개정 이력 3개 이상인 규정 일부의 과거 버전으로 제한한다. ALIO 요청은 속도 제한을 두고 manifest에 출처 URL·해시·수집일을 기록한다.
**이유**: ALIO 파일명의 날짜 표기가 일정하지 않아(연 2자리, 월 단위, 연도 범위) 파일명만으로는 버전을 확정할 수 없다. 법제처 연혁은 버전별 발령일자가 구조화되어 있다. 업스테이지 파서는 페이지당 과금이라 전 버전 파싱은 예산을 넘긴다.
**트레이드오프**: 매칭 실패 파일은 평가에서 빠져 과거 버전 표본이 줄어든다. 법제처 조문과 ALIO 원본이 같은 버전이라도 편집 차이가 있을 수 있어, M2에서 정답 텍스트로 쓸 때 차이를 확인한다.
