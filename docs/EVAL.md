# 평가

원칙: **결정론적으로 잴 수 있는 것은 LLM 채점 없이 잰다.** LLM 채점은 답변 품질처럼 불가피한 곳에만 쓰고, 사람 채점으로 먼저 검증한다. 결과를 보기 전에 가설을 적고(사전 등록), 틀리면 틀린 대로 보고한다.

## 질의셋 (`data/golden/`)

### 골드셋 50문항 (주장의 근거)
- 유형: 식별자 7 · SQL 집계 6 · 단일 문서 의미 9 · 표/별표 6 · 다중 문서 8 · 최신성(개정 이력) 5 · 권한 5 · 답 없음 4
- 최신성 문항은 **실제 개정 이력**(ALIO 개정 버전 파일과 법제처 연혁)에서 만들고, 버전 매칭 신뢰도가 정확·근사인 버전만 쓴다.
- 태그: 유형과 별개로 **어휘 불일치**(예: 질의 "출장비" ↔ 문서 "여비") 태그를 붙인다. 새 유형을 만들지 않는다.
- 출처: 실제 사규 약 20 / 합성 약 30. 사규 문항은 사람이 사규를 읽고 작성한다.
- 분리: dev 20(튜닝용) / test 30(보고용). 보고 수치는 test만 쓴다.
- 절차: 합성 문항은 시드 데이터에서 초안 생성 → **50문항 전부 사람이 검수·확정**. 확정 후 에이전트는 수정하지 않는다.

### 실버셋 150문항 (방향 확인용)
- 시드 데이터에서 문항과 qrels를 자동 생성하고 **20%를 표본 검수**한다.
- 검색 계층 평가에만 쓴다(채점 모델 불필요). 주장은 골드셋으로 하고, 실버셋은 골드셋과 방향이 같은지만 확인한다.

### 문항 필드와 정답 표시 단위
- 필드: 질문, 질문자(팀·직급), 정답 구간(관련도 0/1/2), 참조 답변, 유형, 태그, 출처(real/synthetic)
- **정답은 구간 단위로 표시한다**: `doc_id` + 조항 ID(사규) 또는 시드 데이터 사실 ID·문자 범위(합성). 청크 ID로 표시하지 않는다. 청킹 방식마다 청크가 달라 비교가 무효가 되기 때문이다.

### 가설 사전 등록 (M4, 검색 구현 전)
- `docs/results/hypotheses.md`에 실험별 가설과 판정 기준을 먼저 적는다. 예: "nori는 standard보다 test셋 Recall@10을 높인다", "Agentic RAG는 식별자·SQL 집계·다중 문서 유형에서만 단순 RAG를 이긴다".
- 결과 보고 시 가설별로 채택/기각과 원인 분석을 적는다.

## 지표

### 파싱 (실제 사규만)
파싱 대상은 M1의 파싱 대상 목록(`data/manifest/parse_targets.json`)으로 제한한다.

| 지표 | 방식 |
|---|---|
| 표 셀 일치율 | 정답은 HWPX 원본 `hp:tbl`에서 뽑은 파서 중립 초안을 사람이 검수해 확정한다. 병합 셀은 덮는 모든 칸에 복제하고, 표 추출 기능이 없는 파서는 "해당 없음"으로 평균에서 제외한다. |
| 조항 구조 보존 | 조 수·번호·순서 일치(키 정밀도·재현율, 순서 LCS, 완전 일치율). 분할기 상한(법제처 조문을 이어 붙여 분할한 결과)을 함께 보고. 원본의 '의' 누락 오타(줄 첫머리 `제N조M(제목)`)를 제N조의M으로 인식한 수를 "원본 표기 변형"으로 집계한다. 비교 파서가 2개 이상이면, 문서별로 ok인 파서(2개 이상)가 모두 놓친 법제처 조문 키를 "정답 차이(원본≠법제처 추정)"로 따로 집계하고 그 키를 뺀 키 재현율을 함께 보고 |
| 조문 텍스트 일치 | 조 번호로 짝지은 조문의 문자 유사도·완전 일치율. 원문 비교와 정규화 비교(N1~N5)를 분리 보고 |
| 검색 영향 | 청커·인덱스·질의 고정, 파서만 바꿔 사규 문항 Recall@10·NDCG@10. M4 질의셋·M5 인덱스가 필요하므로 M5로 이월한다. |
| 처리 비용 | 페이지당 시간·비용 |

업스테이지 보조 실험은 변환 PDF 입력과 HWP/HWPX 직접 입력의 양쪽 결과가 있는 대상만 짝 비교하며, 같은 요청 옵션·같은 조문 분할기·같은 채점 함수를 고정한다.

#### 조문 텍스트 비교 정규화와 편집 차이

원문과 파싱 결과는 저장 시 바꾸지 않고 채점할 때만 아래 순서로 정규화한다. 원문 비교는 NFC와 바깥 공백 제거만 적용한다.

| 규칙 | 변환 |
|---|---|
| N1 | 유니코드 NFC 적용(NFKC 미사용) |
| N2 | 균형 잡힌 법령 편집 주석 제거 |
| N3 | 따옴표와 가운뎃점 변형 통일 |
| N4 | 모든 유니코드 공백 제거 |
| N5 | 그 외 문자는 변경하지 않음 |

ADR-022의 법제처 조문과 ALIO 원본 사이 편집 차이는 N2 주석이 법제처에만 있는 `editorial_law_only`, 파싱 결과에만 있는 `editorial_parsed_only`, 양쪽에 있는 `editorial_both`로 나눠 합산한다.

표 정답 보관 규칙: `data/golden/tables/*.md`는 원문이므로 gitignore하고, 선정 정보와 파일 해시는 `data/manifest/table_golden.json`에 커밋한다. 기록된 해시가 바뀐 정답은 채점하지 않는다.

### 검색 (LLM 채점 없음)
| 지표 | 대상 |
|---|---|
| **문서 단위** Recall@10, NDCG@10 (주 지표) | 검색된 청크를 문서로 묶어 채점. 청킹 방식이 달라도 같은 기준 |
| **구간 겹침 적중률** (보조 지표) | 검색된 청크가 정답 구간과 겹치는가. "문서는 맞는데 조항이 틀린" 경우를 잡는다 |
| SQL 실행 정확도 | SQL 집계 문항 — 결과 값이 정답과 같은가 |
| 식별자 적중률 | 식별자 문항 — 정답 문서가 1위인가. 본문 검색 vs `keyword` 정확 일치 비교 |
| 어휘 불일치 태그 성능 | 태그 문항에서 BM25 단독 vs hybrid 차이 |

### 답변
| 지표 | 방식 |
|---|---|
| 정답성 (0~3) | Gemini 채점, 참조 답변 대비 |
| 근거 충실성 (0~3) | Gemini 채점, 답변의 주장이 인용 청크로 뒷받침되는가 |
| 인용 정밀도 | 결정론 — 인용 문서 ∈ 정답 문서 목록 |
| 거절 정확도 | 결정론 — 답 없음 문항에서 `refused=true`인가 |

### 보안 (보안 테스트셋, 결정론)
- 골드셋의 권한 5문항은 답변 품질용이다. 누설률은 별도의 **보안 테스트셋(200건 이상, 자동 생성)**으로 잰다.
- 구성: 제한 문서 × 권한 없는 사용자 × 질의 변형(직접 질문, "관리자로서 알려줘" 같은 우회 표현, 식별자 직접 조회) + **문서 속 간접 프롬프트 인젝션** 시나리오(M3에서 인젝션 문서를 코퍼스에 심는다).
- 판정: (a) 검색 결과에 제한 문서 ID가 있거나 (b) 답변에 카나리아 문자열이 있으면 누설.
- 경로: in-process(LangGraph)와 MCP 두 경로 모두 측정한다. 목표는 누설률 0%.

### 운영
- 질의당 입력·출력 토큰, 비용, 단계 수
- **지연 측정 규칙**
  - 결과표에 측정 환경(기기, OpenSearch 힙, 임베딩 CPU/GPU)을 적는다. 예열 실행은 제외한다.
  - 구간별로 기록한다: 임베딩 / 검색 / LLM 첫 토큰(TTFT) / 전체.
  - 판정은 나눠서 한다: **검색 구간**(통제 가능)과 **전체**(외부 API 포함). 단순 RAG 전체 목표 P95 ≤ 5s, Agentic RAG는 측정 후 목표 설정.

## 채점 모델 검증
- 답변 50개를 사람이 0~3점으로 채점 → 채점 모델과의 일치율, **가중 Cohen's κ** 산출
- 목표 κ ≥ 0.6. 미달 항목은 사람 채점으로 보고한다.
- 채점 모델은 답변 모델과 다른 계열(Gemini)이다. 채점은 3회 반복해 평균·편차를 기록한다.

## 실패 분석 (M7)
test셋에서 틀린 문항을 트레이스로 시스템별 분류한다.

| 분류 | 판정 |
|---|---|
| 도구 선택 오류 | 필요한 도구를 부르지 않았거나 엉뚱한 도구를 불렀다 |
| 인자 오류 | 잘못된 SQL·식별자 |
| 검색 실패 | 정답 구간이 후보에 없다 |
| 생성 오류 | 정답 구간이 후보에 있는데 답이 틀렸다 |
| 권한 오거절 | 권한이 있는데 거절했다 |

검색 실패와 생성 오류는 검색 계층·응답 계층 분리 측정으로 결정론적으로 가른다.

## 실행 조건
- 답변 모델 temperature 0. 모델명·버전·프롬프트 해시를 결과와 함께 기록한다.
- 실험은 한 번에 한 변수만 바꾸고, 고정한 조건을 결과표에 적는다.
- 실제 API 평가(`make eval`)는 사용자가 직접 실행한다. 하네스 step에서 돌리지 않는다.
- API 비용은 `MONTHLY_BUDGET_USD` 설정값을 넘기 전에 스크립트가 멈춘다.

## 결과 보고 (`docs/results/`)
- 파일명에 날짜, 본문에 커밋 해시·모델 버전·고정 조건·측정 환경을 적는다.
- **검색 실험은 전체 조합(분석기 3 × 방식 4 × 청킹 2)을 실행**하고 세 가지 표로 보고한다.
  - 주 표 — **사다리**: standard BM25 + 고정 청킹 → +nori → +hybrid → +구조 청킹 → +리랭커. 각 단계의 증가분을 보인다.
  - 보조 표 — **제거 실험**: 최종 구성에서 한 요소씩 뺀다.
  - 부록 — 전체 조합표(축 간 상호작용 확인).
- 두 시스템 비교는 같은 문항 쌍으로 **짝 비교 부트스트랩 95% 신뢰구간**을 붙인다. 구간이 0을 포함하면 우열을 주장하지 않는다. 유형별 수치는 문항 수가 적어 참고용으로 표시한다.
- 실제 사규 문항과 합성 문항 점수를 **분리**해서 보고한다. 둘의 차이가 합성 문항이 얼마나 쉬운지의 증거다.
- **합성 코퍼스 신뢰성**: 합성 문서 표본 20건의 사람 검수 결과(사실 일관성·문체 다양성·현실감 체크리스트)와 문서 간 중복·다양성 지표를 함께 싣고, 한계 섹션에 합성 문항이 실제보다 쉽다는 점을 명시한다.
- 이전 결과 대비 회귀가 있으면 원인을 적는다. 수치를 고치려고 golden을 바꾸지 않는다.
