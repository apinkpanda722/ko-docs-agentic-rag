## 2. 권장 실행 순서

1. `make parse-pypdf`
2. `make parse-score`
3. `data/interim/parse_diffs/pypdf/`와 분할기 상한 결과로 분할 결과를 육안 확인한다. 분할기 규칙 문제면 여기서 고친다.
4. `make docling-models` → `make parse-docling`
5. `make parse-upstage-dry`로 예상 비용을 확인한다.
6. `make parse-upstage`
7. `make table-drafts` → 사람이 약 10개를 검수해 `data/golden/tables/`에 확정 → `make table-golden` → `make table-score`
8. `make parse-score` → `make parse-report`
9. (보조 실험) 실행 전 업스테이지 콘솔 Usage 쪽수 기록 → `make parse-upstage-direct-dry` → `make parse-upstage-direct` → 실행 후 콘솔 Usage 쪽수 기록, 원장(`costs.jsonl`)의 쪽수 합과 대조 → `make parse-score` → `make table-score` → `make parse-report`

## 3. 고정 조건

- 입력은 M1에서 변환한 동일 PDF이고 `infra/fontconfig/fonts.conf` 해시를 기록한다.
- 조문 분할기와 채점 코드는 모든 파서에 동일하게 적용한다.
- pypdf는 plain 추출, Docling은 OCR 끔·표 구조 켬, 업스테이지는 `standard`·`ocr=auto`·표 병합 끔으로 고정한다.
- 대상은 115개(현행 95 + 과거 20)다.

## 4. 정규화 규칙과 비교 방식

원문 비교는 유니코드 NFC와 바깥 공백 제거만 적용한다. 정규화 비교는 아래 N1~N5를 순서대로 적용하며, 저장된 원문은 바꾸지 않는다.

| 규칙 | 변환 |
| --- | --- |
| N1 | 유니코드 NFC 적용 |
| N2 | 균형 잡힌 법령 편집 주석 제거: `<개정·신설·삭제·종전 …>`, `[…]`·원본의 `〔…〕` 중 편집 키워드(본조·본항·본호 (+제목) 신설·개정, 전문개정, 제목개정, 종전, 시행일)로 시작하는 주석, 삭제 항목 뒤 날짜 꺾쇠(`삭제 <2002. 1. 1.>`의 `<…>`, "삭제" 단어는 남김). 키워드는 법제처 267개 버전의 `[…]` 795건 전수 집계로 정했고, 내용 괄호(별표·별지·서식·조문 인용·명칭 표기)와 `부칙 <날짜>`는 남긴다 |
| N3 | 따옴표(`` " ' “ ” ‘ ’ ` ´ `` 등)를 `"` 하나로, 가운뎃점(`ㆍ · ․ ‧ ∙` 등)을 `·` 하나로 통일한 뒤 NFKC(전각 콜론·괄호·숫자 등 호환 문자)를 적용하고 다시 통일한다. 원문자 번호(U+2460–U+24FF: ①~⑳, ⑴, ⒜ 등)는 NFKC에서 제외해 그대로 둔다(규정에서 ①은 항, 1.은 호로 구조적 의미가 다르므로 ①→1로 바꾸면 항 번호 오추출이 일치로 숨는다). NFKC를 먼저 하면 `ㆍ`가 조합형 자모로, `․`가 마침표로 바뀌므로 순서를 고정한다 |
| N4 | 모든 유니코드 공백 제거 |
| N5 | 그 외 문자는 변경하지 않음 |

## 7. 변환 경유 vs 직접 입력(업스테이지 보조 실험)

실행 전에 업스테이지 콘솔 Usage 쪽수를 기록한다. `make parse-upstage-direct-dry`로 변환 PDF 쪽수 × 1.5 가정의 예상 비용(세금 10%·청구 여유 5% 포함)을 확인한 뒤 `make parse-upstage-direct`를 사용자가 실행한다. 실행 후 콘솔 Usage 쪽수 증가분을 원장에 새로 기록된 쪽수 합과 대조해 아래 비용 메모에 적는다. 이어서 `make parse-score` → `make table-score` → `make parse-report` 순서로 실행하면 위 생성 결과표에 양쪽 결과가 있는 대상만 짝지은 비교가 추가된다. 실제 HWP/HWPX 과금 쪽수는 응답 `usage.pages`이며 PDF 쪽수와 다를 수 있다.

### 결과 (같은 14개 문서·같은 표 정답 10개 짝 비교)

| 지표 | 변환 PDF | HWP/HWPX 직접 |
| --- | ---: | ---: |
| 조 구조 완전 일치 | 13/14 | 12/14 |
| 키 재현율 평균 | 1.0 | 1.0 |
| 정규화 완전 일치(짝지은 조문 micro) | 76.7% | 75.9% |
| 정규화 유사도(문서 평균) | 0.992 | 0.989 |
| 과금 쪽수 합 | 300 | 276 (-8%) |

- 표: 중첩 표 52871_0-03은 직접 입력에서만 크기(shape)가 일치했다. 칸 일치율은 양쪽 모두 0.67로 같다. 53959_0-04는 칸 일치율이 1.00에서 0.96으로 낮아졌다. 나머지 표는 차이가 없다(생성 결과표 "변환 경유 vs 직접 입력"의 표 셀 일치율 0.967 vs 0.963).
- 과금 쪽수는 직접 입력이 8% 적다. 변환 시 글꼴 대체로 PDF 쪽수가 늘어난 것으로 추정한다(확인하지 않음).
- **결론:** 표본에서 품질 차이가 없다. 변환 경로는 업스테이지 품질을 떨어뜨리지 않는다. 직접 입력의 이점은 쪽수(비용)와 변환 의존성 제거다. HWP 쪽수 추정 계수 1.5는 실측 0.92배(276/300)로 과보수적이다.

## 8. 비용 메모

원장 금액은 **정가 + 부가세 10% 포함**이며 크레딧은 반영하지 않는다. 업스테이지 콘솔 사용량은 VAT 제외라 원장 금액과 다를 수 있다. 콘솔 월 한도($25)는 서비스 쪽 차단으로 원장 상한과 별개다.

### 업스테이지 과금 대조

1차(변환 PDF 입력, 115건):

| 항목 | 원장(`costs.jsonl`) | 업스테이지 콘솔 |
| --- | ---: | ---: |
| 쪽수 | 1887 | 1947 |
| 금액(세전) | $18.87 | $19.47 |
| 크레딧 차감 | 반영 안 함 | -$10.00 (소계 $9.47) |

- 1차(변환 PDF 115건): 콘솔이 원장보다 60쪽(3.2%) 많았다. 응답 `usage.pages` 합은 1887이고 문서별 쪽 번호와 일치했다. 원장과 응답 캐시는 모두 115건이며 추가 호출 기록은 없었다. 콘솔 CSV는 일 합계 한 줄뿐이라 요청 단위로 대조할 수 없었다.
- 2차(직접 입력 14건): 원장 276쪽과 콘솔 증가분 276쪽(1,947→2,223)이 정확히 일치했다. `parse_runs.jsonl`의 `attempts` 기록상 14건 모두 1회 시도·HTTP 200이었다.
- 판단: 1차 +60쪽은 일회성으로 본다. 시도 기록을 도입하기 전의 미기록 재시도로 추정하지만, **원인은 확인하지 못했다.**
- 조치: 예산 검사와 dry-run 예상 비용에만 청구 여유 5%(`billing_margin=1.05`)를 곱하고, 원장은 응답 쪽수 그대로 기록한다. 원인이 확정되지 않아 여유는 유지한다(ADR-023).
- 콘솔 월 한도는 크레딧 차감 후 청구액 기준이다.

## 9. 한계

- 검색 영향(Recall@10)은 M4 질의셋과 M5 인덱스가 필요하므로 M5로 이월한다.
- 쪽수는 대체 글꼴에 좌우된다.
- 여러 쪽 표는 엄격하게 채점한다.
- 법제처 조문과 ALIO 원본 사이에 편집 차이가 있을 수 있다.
- Docling은 기본 PDF 백엔드 기준이다. 한글 조 번호 글자 누락(25키)은 백엔드 교체로 달라질 수 있으나 파서 설정 고정 원칙에 따라 실험하지 않는다.
- 법제처 본문에 조문 텍스트가 없는 버전은 생성 결과표에 파싱 대상 밖 버전까지 싣는다. M4 질의셋 작성 시 이 규정은 조항 단위 정답을 법제처에서 얻을 수 없다고 기록한다.
