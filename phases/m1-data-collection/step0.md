# Step 0: docs-decisions

## 읽어야 할 파일

먼저 아래 파일들을 읽고 프로젝트의 기획·아키텍처·설계 의도를 파악하라:

- `AGENTS.md` — CRITICAL 규칙 전체
- `docs/PRD.md` — "코퍼스" 절, 마일스톤 표의 M1 행
- `docs/ADR.md` — ADR-001, ADR-002, ADR-008, ADR-020
- `docs/ARCHITECTURE.md` — 디렉토리 구조, 데이터 흐름
- `docs/EVAL.md` — "골드셋 50문항"의 유형 목록(최신성 항목)

## 배경

M1(data-collection)을 시작하기 전에 대상 기관과 원문 사용 방식이 확정됐다. 이 step은 **문서만** 고쳐
이후 step(코드)이 바뀐 결정을 읽고 작업하게 한다. 확정된 사실은 아래와 같다. 이 사실은 사용자가 조사해
확정했으므로 그대로 반영하고 다시 판단하지 마라.

- 대상 기관은 **NIA(한국지능정보사회진흥원)** 로 확정했다. ALIO 기관 ID는 `C0392`, 내부규정은 95개다.
  ALIO 원본 파일은 HWP 위주이고 최근 개정본은 HWPX이며, 개정 버전별 파일과 과거 버전 zip 취합본이 있다.
- 국가법령정보센터에 95개 규정 전부의 구조화 조문이 있고, 법제처 Open API(`target=pi`, 공공기관 규정)의
  목록·본문 API로 받을 수 있다. 본문에는 조문·부칙·별표 목록이 들어 있다. `nw=2`로 조회하면 과거 버전(연혁)
  목록과 버전별 발령일자를 받을 수 있다.
- KISA·NIA·NIPA 모두 ALIO에 공공누리 표시가 없다. 그래서 **기관명 치환 같은 가공을 하지 않는다.**
  원문은 무가공으로 로컬에서만 쓰고(커밋·재배포하지 않음), 합성 문서는 기관명 없이 규정명·조항만 참조한다.
- 수집은 두 경로다. ① 법제처 Open API: 구조화 조문과 별표 목록 = **파싱 정답 텍스트**, 버전별 발령일자 =
  **개정 날짜의 기준**. ② ALIO 원본 파일(HWP/HWPX, 개정 버전별) = **파싱 입력**이자 **실제 개정 이력**.
- ALIO 파일명의 날짜 표기는 제각각이라(`(15.5.12)`, `_20210316`, `(2024년도 11월 개정)`) 참고용이다.
  ALIO 파일은 법제처 버전과 발령일자로 짝지어 매칭 근거와 신뢰도(정확/근사/실패)를 기록하고, 매칭 실패 파일은
  파싱 평가 대상에서 제외한다.
- 법제처 응답에는 담당자명·전화번호가 들어 있다. 원본 응답은 `data/raw/`에만 두고, 정제 산출물(`data/interim/`)과
  manifest에는 넣지 않는다. `data/interim/`도 원문을 담으므로 커밋하지 않는다.
- 업스테이지 파서는 페이지당 과금이라 전 버전을 파싱하지 않는다. M2 파싱 대상은 현행본 전부 + 개정 이력 3개 이상인
  규정 일부의 과거 버전으로 제한하고, M1에서 예상 페이지 수를 포함한 대상 목록을 만든다.
- HWP·HWPX → PDF 변환은 LibreOffice + H2Orestart(0.7.14)다. H2Orestart는 HWP 5.x와 HWPX를 모두 지원한다
  (확장이 등록하는 파일 유형의 확장자가 `hwpx hwp`). 사용자가 로컬에서 두 형식 모두 변환에 성공했다.

## 작업

### 1. `docs/ADR.md`

**ADR-001** — 결정 문장의 "ALIO 공공기관 내부규정(사규)과 법제처 행정규칙"을
"ALIO 공공기관 내부규정(사규) 원본 파일과, 같은 규정의 법제처 Open API 구조화 조문(파싱 정답 텍스트)"으로 바꾼다.
나머지 문장은 유지한다.

**ADR-002** — 제목과 본문을 아래 내용으로 교체한다(문장은 다듬어도 되지만 결정 내용을 바꾸지 마라).

- 제목: `ADR-002: 가상 IT 서비스 회사, 실제 규정은 NIA 내부규정 원문을 무가공 로컬 사용`
- 결정: 가상 회사(약 200명, 8개 팀) 설정은 유지한다. 실제 규정은 NIA ALIO 공시 내부규정 95개를 원문 그대로
  로컬에서만 쓴다. 기관명 치환 등 가공은 하지 않는다. 합성 문서는 기관명 없이 규정명·조항만 참조한다
  (예: "여비규정 제8조"). 원문과 정제 산출물은 커밋하지 않고 manifest(출처 URL·해시·수집일)로 재현한다.
- 이유: 후보 세 기관 모두 ALIO에 공공누리 표시가 없어 기관명 치환(2차적 저작물 작성)의 근거가 없다.
  무가공 원문을 재배포하지 않고 로컬 평가에만 쓴다. 실존 기관 이름으로 회의록·티켓 같은 기록을 만들면 허위 기록이
  되므로 합성 문서에는 기관명을 쓰지 않는다. NIA는 규정 95개가 법제처에 구조화 조문으로 모두 있어 파싱 정답을
  자동으로 얻을 수 있고, 정보화·AI 관련 규정이 IT 회사 설정과 맞으며, HWP·HWPX 개정 버전 파일이 있어 실제 개정 이력을 쓸 수 있다.
- 트레이드오프: 규정 본문에 실제 기관명이 남아 가상 회사 설정과 이음새가 보인다. 저장소만으로는 재현되지 않고
  사용자가 수집 스크립트를 실행해야 한다. 법제처 응답의 담당자 개인정보(담당자명·전화번호)는 정제 산출물과 manifest에서 제거한다.

**ADR-008** — 결정 문장의 변환 경로를 "HWP·HWPX → LibreOffice + H2Orestart → PDF"로 바꾸고,
"H2Orestart는 HWP 5.x와 HWPX를 모두 지원한다"는 문장을 이유에 추가한다. 변환 형식은 확장자가 아니라 파일 시그니처
(HWP 5.x는 OLE 복합 문서, HWPX는 zip)로 판정한다는 문장을 결정에 추가한다.

**ADR-020** — 삭제하지 말고 제목에 `(폐기)`를 붙이고, 본문 맨 앞에 상태 줄을 추가한다:
"**상태**: 폐기 — ADR-002 개정으로 원문을 가공하지 않게 되어, 공공누리 유형에 따라 다른 기관이나 행정규칙으로
대체할 필요가 없어졌다." 기존 결정·이유·트레이드오프 문장은 이력으로 남긴다.

**ADR-022 (신규, 파일 끝에 추가)** — `ADR-022: 규정은 두 경로로 수집하고, 개정 날짜는 법제처 연혁을 기준으로 삼는다`
- 결정: 법제처 Open API에서 현행·연혁 버전의 본문을 모두 받아 파싱 정답과 개정 날짜 기준으로 쓴다. ALIO 원본
  파일(zip 취합본은 압축 해제)은 파싱 입력으로 쓴다. ALIO 파일마다 법제처 버전과 발령일자로 매칭해 근거와
  신뢰도(정확/근사/실패)를 manifest에 남기고, 실패 파일은 파싱 평가 대상에서 제외한다. 파싱 대상은 현행본 전부와
  개정 이력 3개 이상인 규정 일부의 과거 버전으로 제한한다. ALIO 요청은 속도 제한을 두고 manifest에 출처 URL·해시·수집일을 기록한다.
- 이유: ALIO 파일명의 날짜 표기가 일정하지 않아(연 2자리, 월 단위, 연도 범위) 파일명만으로는 버전을 확정할 수 없다.
  법제처 연혁은 버전별 발령일자가 구조화되어 있다. 업스테이지 파서는 페이지당 과금이라 전 버전 파싱은 예산을 넘긴다.
- 트레이드오프: 매칭 실패 파일은 평가에서 빠져 과거 버전 표본이 줄어든다. 법제처 조문과 ALIO 원본이 같은 버전이라도
  편집 차이가 있을 수 있어, M2에서 정답 텍스트로 쓸 때 차이를 확인한다.

### 2. `docs/PRD.md`

- "코퍼스"의 **실제 문서** 줄을 교체한다: NIA(한국지능정보사회진흥원) ALIO 공시 내부규정 95개, 원문 무가공·로컬 전용(ADR-002).
  HWP·HWPX, 조·항·호 구조, 별표 표. 법제처 Open API 구조화 조문을 파싱 정답 텍스트로 쓴다.
  **최신성 문항의 출처는 실제 개정 이력**(ALIO 개정 버전 파일 + 법제처 연혁, ADR-022)이다.
- 마일스톤 표 M1 행: 산출물을 "법제처 Open API·ALIO 수집 스크립트, manifest(출처·해시·수집일), ALIO↔법제처 버전 매칭,
  HWP/HWPX→PDF 변환, M2 파싱 대상 목록(예상 페이지 수)"로, 사용자 작업을 "법제처 인증키 입력, LibreOffice+H2Orestart 설치,
  수집·변환 명령 실행"으로 바꾼다.

### 3. `docs/EVAL.md`

골드셋 유형 목록의 `최신성(개정 이력) 5`에 출처를 덧붙인다: 최신성 문항은 **실제 개정 이력**(ALIO 개정 버전 파일과 법제처 연혁)에서
만들고, 버전 매칭 신뢰도가 정확·근사인 버전만 쓴다. 파싱 지표 절에 "파싱 대상은 M1의 파싱 대상 목록(`data/manifest/parse_targets.json`)으로 제한한다"를 추가한다.

### 4. `docs/ARCHITECTURE.md`

- `ingest/` 설명: `# 법제처 Open API·ALIO 수집, ALIO↔법제처 버전 매칭, HWP/HWPX → PDF 변환, 파싱 대상 목록, manifest 기록`
- `data/` 트리에 `interim/  # 정제 산출물(법제처 응답에서 담당자 정보 제거 등) (커밋 안 함)`을 `raw/` 아래에 추가한다.
- `data/manifest/` 설명을 "원문 출처·해시·수집일·버전 매칭·변환 기록·파싱 대상 목록 (커밋)"으로 바꾼다.
- 데이터 흐름의 첫 줄을 두 경로로 바꾼다. 예:
  ```
  법제처 Open API(현행·연혁 조문·별표 목록) → 정제 JSON ─────────────┐ (파싱 정답·개정 날짜 기준)
  ALIO 사규(HWP/HWPX, 개정 버전) → 버전 매칭 → HWP/HWPX→PDF → 파서 → 조문 분할 → 구조 청킹 ─┐
  ```
  기존 흐름의 나머지 줄은 유지하고 화살표가 자연스럽게 이어지게 다듬는다.

### 5. `AGENTS.md`

- CRITICAL 규칙 "합성 문서는 가상 회사 이름으로만 만든다…" 줄 끝에 "실제 규정은 기관명 없이 규정명·조항만 참조한다." 를 추가한다.
- `data/raw/` CRITICAL 규칙 바로 아래에 새 CRITICAL 규칙을 추가한다:
  "CRITICAL: `data/interim/`(정제 산출물)도 원문을 담으므로 커밋하지 않는다. 법제처 응답의 담당자명·전화번호는 정제 산출물과 manifest에 넣지 않는다. 법제처 인증키(`OC`)는 로그·manifest·예외 메시지에 남기지 않는다."
- 명령어 절은 이 step에서 바꾸지 마라(각 make 타깃은 그것을 추가하는 step에서 올린다).

## Acceptance Criteria

```bash
make verify
grep -n "ADR-022" docs/ADR.md
grep -n "(폐기)" docs/ADR.md
grep -n "실제 개정 이력" docs/PRD.md docs/EVAL.md
grep -n "data/interim/" AGENTS.md
```

## 검증 절차

1. 위 AC 커맨드를 실행한다. grep이 각각 한 줄 이상 찾아야 한다.
2. 아키텍처 체크리스트를 확인한다:
   - 결정 내용이 위 "배경"의 확정 사실과 어긋나지 않는가?
   - 기존 ADR 번호를 바꾸거나 기존 ADR을 삭제하지 않았는가?
3. 결과를 최종 응답(JSON)으로 보고한다. `phases/` 아래 파일은 수정하지 않고 git commit도 하지 않는다:
   - 성공 → `"status": "completed"`, `"summary": "산출물 한 줄 요약"`
   - 해결할 수 없는 실패 → `"status": "error"`, `"reason": "구체적 에러 내용"`
   - 사용자 개입 필요 → `"status": "blocked"`, `"reason": "구체적 사유"` 후 즉시 중단

## 금지사항

- 코드·테스트·`Makefile`·`.env.example`·`pyproject.toml`을 수정하지 마라. 이유: 이 step은 문서만 다룬다. `.env.example`의
  `LAW_OPEN_API_KEY`는 설정 로더와 동기화 테스트가 묶여 있어 step 1에서 코드와 함께 추가한다.
- 네트워크 요청을 하지 마라(법제처·ALIO 포함). 이유: 실제 수집은 사용자가 실행한다(ADR-014).
- ADR-020을 삭제하거나 번호를 재사용하지 마라. 이유: 결정 이력은 남긴다.
- 법률 해석을 단정하는 문장(예: "합법이다", "저작권 문제가 없다")을 쓰지 마라. 이유: 확인된 사실(공공누리 표시 없음, 가공·재배포하지 않음)만 적는다.
- `data/golden/`을 만들거나 수정하지 마라.
- 기존 테스트를 깨뜨리지 마라.
