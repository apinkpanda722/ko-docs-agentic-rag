# Step 0: design-docs

## 읽어야 할 파일

먼저 아래 파일들을 읽고 프로젝트의 아키텍처와 설계 의도를 파악하라:

- `AGENTS.md` — 아키텍처·개발 프로세스 CRITICAL 규칙 (retrieval의 langchain/langgraph 금지, 모든 검색은 authorized_*, LLM·외부 API mock, golden·raw·interim 비커밋)
- `docs/ARCHITECTURE.md` — 디렉토리 구조·패턴·상태 관리
- `docs/ADR.md` — ADR-005·006·007·009·010·013·015·016·017·026·028(M5 설계, step 0에서 추가됨)
- `docs/EVAL.md` — 검색 지표·결과 보고 절
- `docs/results/hypotheses.md` — H1~H7과 "M5 판정 규칙" 절(step 0에서 추가됨)
- `docs/results/2026-09-28-m4-golden-set.md` — M4 결과·한계(코퍼스 표현 반복, 개정 전 버전 선행 조건)
- `data/manifest/golden_review.json` — split 통계, `retrieval_test_n`, H7 문항 수

이전 step에서 만들어진 코드를 꼼꼼히 읽고, 설계 의도를 이해한 뒤 작업하라. 이 phase의 결정(ADR-028)과 판정 규칙(hypotheses.md의 "M5 판정 규칙")은 사전 등록된 값이므로 바꾸지 마라.

## 작업

이 step은 코드 없이 결정 문서만 쓴다. 아래 수치와 규칙은 사용자와 확정한 값이므로 바꾸지 마라. 이후 step은 이 문서를 기준으로 구현한다. 작성일은 2026-09-30이다.

### 1. `docs/ADR.md`에 ADR-028 추가 — M5 검색 실험 설계

기존 ADR 형식(**결정**/**이유**/**트레이드오프**/필요 시 **변경 기록**)을 따르고, 결정에 아래를 모두 적는다.

1. **범위**: 분석기는 standard·nori 두 개. n-gram은 제외하며 사유는 "사전 등록 가설 H1~H7 어디에도 n-gram이 걸려 있지 않아 판정에 필요 없고, 범위 축소 순서상 뒤쪽 항목"이다. 방식 4개(BM25, kNN, hybrid-RRF(rank_constant=60), hybrid-가중합(min-max 정규화)), 청킹 2개(고정·구조). 식별자는 `keyword` 필드 + `term` 쿼리. 리랭커는 M8.
2. **실행 조합 수**: 명목 2×4×2=16이지만 kNN은 분석기와 무관(같은 벡터)하므로 청킹당 1회만 실행한다. 실제 실행·보고 조합은 BM25 4 + RRF 4 + 가중합 4 + kNN 2 = **14**. 결과 문서에 "명목 16, kNN 두 행 합쳐 14"를 그대로 적는다.
3. **보고 표**: 주 표 사다리(standard BM25+고정 → nori BM25+고정 → nori+hybrid+고정 → nori+hybrid+구조), 보조 표 제거 실험(최종 구성에서 한 요소씩 뺌: 구조→고정, hybrid→BM25, nori→standard), 부록 전체 조합표.
4. **지표**: 문서 단위 Recall@10(정답 = 관련도 ≥ 1), NDCG@10(이득 = 관련도 0/1/2 그대로 선형). 문서 단위 지표는 qrels를 doc_id별 최대 관련도로 합쳐 계산하고, 청크 순위는 문서별 최대 점수로 묶어 상위 10 문서를 쓴다. 구간 겹침 적중률(H3·보조): 상위 10 청크 중 하나라도 관련도 ≥ 1인 qrels 구간(같은 doc_id)과 문자 범위가 겹치면 적중. 실제 규정 qrels는 조 키·별표 id를 청커 쪽 조·별표 범위로 바꿔 대조한다.
5. **인덱스 구조**: 청킹·파서 조건당 인덱스 1개. 텍스트 필드 `text_std`·`text_nori` 두 개(BM25 통계는 필드별이므로 분석기별 인덱스와 동등), `knn_vector`(BGE-M3 1024차원), 식별자 `keyword` 필드, 권한 필드. 인덱스는 합성 문서 200건 + 실제 규정 + 개정 전 5건을 모두 담는다. 청킹 비교용 2개(조합본 고정·구조) + 파서 탐색 비교용 2개(pypdf 단독 구조·업스테이지 단독 구조) = 인덱스 4개.
6. **실제 규정 본 인덱스 텍스트 = 조합본**: M2 결론(조문은 pypdf, 별표 표는 업스테이지)을 따른다. 조문 청크는 pypdf 텍스트에서 만들고 pypdf 텍스트의 별표 영역은 제외한다. 별표는 업스테이지 표를 별표 id에 붙여 표 단위 청크로 만든다. 고정 청킹용 문서 텍스트는 [pypdf 조문 영역 + 업스테이지 별표 표 텍스트]를 이어 붙인 것이다. 이유: 업스테이지 조 구조 일치율이 85.1%(pypdf 98.2%)라 구조 청킹과 조 단위 qrels 매핑이 불리해져 H3가 치우친다. 업스테이지 표→별표 id 매핑 규칙은 대상 115개 전체에 돌려 매핑 실패 건수를 센 뒤 확정하고(FP-016), 실패한 별표는 pypdf 별표 텍스트로 대체하며 목록을 manifest에 남긴다(step 2).
7. **개정 전 5건**: temporal:revision 5문항의 정답 규정마다 법제처 연혁의 직전 개정 버전을 인덱스에 넣는다. 텍스트는 법제처 연혁 조문(`data/interim/law`)이며 파서와 무관하게 고정된다. 현행 문서(파싱본)와 형식이 달라 치우칠 수 있으므로, temporal 문항마다 "개정 전 문서가 현행 문서보다 위에 나온 경우"(두 문서의 순위)를 기술 통계로 결과 문서에 보고한다.
8. **고정 청킹 크기**: 512토큰도 500자도 쓰지 않는다. 고정 청크 크기 = 전체 코퍼스(조합본 구조 청킹) 구조 청크 길이(문자)의 중앙값을 50자 단위로 반올림한 값, 겹침 = 그 값의 20%. step 4에서 계산해 `data/manifest/m5_index.json`과 이 ADR에 기록하며 검색 결과를 보기 전에 확정한다. 이유: 청크 크기 효과를 통제하고 경계 효과만 비교하기 위해.
9. **측정 조건 고정**: H1·H2는 사다리 인접 단계로 고정 청킹에서 측정한다(H1 = standard BM25 vs nori BM25, H2 = nori BM25 vs nori hybrid). H3은 nori hybrid(최종 hybrid 방식·파라미터)에서 구조 vs 고정. H4의 keyword 방식은 식별자 `term` 필터로 후보를 좁힌 뒤 질문 텍스트의 nori BM25 점수로 정렬해 1위를 정하고(식별자가 여러 문서에 나오므로 결정론적 순서가 필요), 대조군은 최종 구성(nori hybrid + 구조 청킹) 본문 검색이다. 질문에서 식별자를 못 뽑으면 미적중으로 센다. H7은 최종 구성에서 판정한다. 채택 = 95% CI가 가설 방향으로 0을 배제. 반대 방향으로 0을 배제하면 "기각(반대 방향)", 0을 포함하면 "판정 보류(차이 입증 못 함)". 보고 대상은 골드 test 검색 지표 대상 21문항(H7은 합성 8·실제 6)이다.
10. **튜닝**: hybrid 파라미터(가중합의 BM25 가중치, 후보 청크 수 top-k, RRF vs 가중합 선택)는 골드 dev(검색 지표 대상 14)와 실버 dev(검색 지표 대상 43)로만 조정한다. 조정은 nori + 고정 청킹 hybrid에서 하고 같은 파라미터를 구조 청킹에도 쓴다. 선택 점수 = (골드 dev 평균 NDCG@10 + 실버 dev 평균 NDCG@10) / 2, 동점이면 RRF, 그다음 작은 후보 수. 확정 설정은 `data/manifest/m5_config.json`에 해시와 함께 고정한다.
11. **test 실행 잠금**: test는 확정 설정으로 한 번 실행한다. 실행 설정 해시를 결과에 기록한다. 재실행은 막힌 채로 두지 않되 `--rerun-reason "<사유>"`가 있어야 하며, 사유·날짜·이전 결과 해시를 실행 기록에 누적한다. 결과 문서에는 첫 실행과 재실행 결과를 모두 보고한다.
12. **평가 전제 검사**: 평가 질의는 각 문항의 asker 권한으로 검색한다. rel ≥ 1인 qrels 문서가 asker에게 보이는지 전수 검사하고, 안 보이는 문항은 목록과 함께 실패로 멈춘다(자동 제외 금지).
13. **answer_repeated 보조 분석(판정 아님)**: 각 문항에 결정론 태그를 붙인다. 정의 = 정답 근거 문장을 공백·문장부호 정규화했을 때 코퍼스의 서로 다른 2개 이상 문서에 동일하게 나타남. 근거가 여러 개인 문항은 rel=2 근거 중 하나라도 반복이면 참. 실제 규정은 같은 rule_id의 버전들을 한 문서로 센다. 태그와 그룹별 문항 수(골드 test·실버 test × 출처 × 반복 여부)는 step 11에서 manifest에 기록하며 `make m5-test` 전에 확정한다. H2(NDCG@10, hybrid − nori BM25)를 출처별·answer_repeated별로 나눠 기술 통계로 보고한다.
14. **코퍼스 v2 착수 조건(이것만으로 결정)**: 실버 test에서 (hybrid − nori BM25) NDCG@10 차이의 [반복 아님 − 반복] 값에 대해 독립 표본 부트스트랩 95% CI(10,000회)의 하한이 0.10 이상이면 코퍼스 v2를 별도 phase로 제안한다. 반복/반복 아님 중 한 그룹이라도 10문항 미만이면 "판정 불가(표본 부족) = 코퍼스 v2 미착수, 한계로 기록". 아니면 한계로만 기록하고 진행한다.
15. **파서 탐색 비교(사전 등록 가설 아님, "탐색적 비교"로 표시)**: 3조건 — pypdf 단독 / 업스테이지 단독 / 조합본(본 인덱스). 청킹(구조)·인덱스 설정·질의·최종 hybrid 설정을 고정하고 파서 조건만 바꾼다. 대상은 실제 골드 검색 지표 대상 19문항(dev 6 + test 13)이며 test 13 부분집합은 따로 표시한다. 기술 통계와 짝 비교 부트스트랩 95% CI를 함께 보고한다.
16. **LLM 호출 없음**: 이 phase의 코드는 LLM·외부 API를 호출하지 않는다. 임베딩은 로컬 BGE-M3다.

ADR-028 아래에 **변경 기록** 소절을 두고, 이후 값 확정(고정 청크 크기)이 여기 기록되도록 자리를 만든다.

## 금지사항

- 네트워크 요청·다운로드·패키지 설치를 하지 마라. 이유: 지시에 없는 외부 접근은 사전 승인 대상이다(FP-040). 새 의존성이 필요해 보이면 `blocked`로 보고한다.
- LLM·외부 API를 호출하거나 `anthropic`·`openai`·`google.genai`·`kodocs.llm`을 import하지 마라. 이유: M5는 결정론 검색 실험 phase이며 LLM 호출이 생기면 멈추고 보고하는 조건이다.
- `.env`를 열거나 출력하지 마라. `data/golden/`(질의셋·qrels·사람 채점)을 수정하지 마라. 이유: 사람이 확정한 기준이며 수치를 맞추려고 바꿀 수 없다.
- `data/raw/`·`data/interim/`를 커밋 대상으로 만들지 마라(gitignore 유지). 이유: 원문이 들어 있다. manifest에는 해시·개수·id만 남기고 조문·표 원문 텍스트를 넣지 마라.
- `phases/` 아래 파일을 수정하거나 git commit을 하지 마라. 이유: index.json은 execute.py만 수정한다.
- `src/kodocs/retrieval/`에서 `langchain`·`langgraph`·`kodocs.agent`·`kodocs.mcp_server`·`kodocs.ui`를 (상대 import 포함) import하지 마라. 이유: 검색은 측정 대상이라 추상화 없이 OpenSearch·SQLite를 직접 호출한다(ADR-009).
- 기존 테스트를 깨뜨리지 마라
